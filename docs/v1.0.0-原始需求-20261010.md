# 原始需求

## 目标

设计并开发一个“中国古典诗词格律检测”的npm算法包。

全称: `cn-poetry-meter-check`，缩写 CPMC，其中 cn 表示Chinese是中国的意思。

版本: v1.0.0

## 内容

设计开发的要点包括以下内容：

1. 完整的中国古典诗词格律检测算法
2. 一个简单示例的html页面，用于手动验证检测结果
3. 算法的接口测试
4. API使用文档（只提供中文文档说明）
5. MIT协议，README.md（只提供中文文档说明）
6. 其他常规的npm包文件

## 具体说明

### 基础检测算法

1. 格律检测算法至少包括：五言绝句、五言律诗、七言绝句、七言律诗
2. 检测平仄，不符合平仄给出具体错误提示。
3. 检测押韵，律诗首句不入韵和入韵区分。该押韵的不押韵就给出错误提示
4. 检测拗句、孤平、出律、失粘、拗体情况。给出具体的错误提示
5. 检测自救情况。此句自救属于正常补救方法，不认为错误，给出提示即可
6. 检测多音字导致的平仄可能存在的情况，这里算法无法从语义方式判定多音字，只能给出警告建议，拿“长”举例：颔联对句第三字[长·平水韵 七阳平声]当为平，若取[平水韵 二十二养上声]或[平水韵 二十三漾去声]则出律/孤平。类似这样检测结果描述。
7. 需要支持韵表，默认平水韵，还要支持词林正韵、新韵、通韵等

### 高级检测算法

可能涉及到大模型或者AI算法。以下算法分别可以保留一套稳定的API，具体的内部实现可以留空，一般用户自己有能力可以识别对仗多音字等，后续有具体的方案可以补充具体实现即可。

1. 失对

律诗可能要求颔联、颈链对仗，一般算法无法检测，需要通过大模型进行AI检测。建议：全网搜索是否有对仗检测的大模型、算法库等。如果没有则暂且提供一套API，支持通过简单的API算法或者提供大模型APIKEY接入，APIKEY后续重点说明逻辑，如qwen、deepseek、kimi的llvm模型。

2. 多音字

对于基础检测算法中给出的提示中，如果能明确知道使用哪个韵表的哪个部，则不需要给提示了。比如长风，这里面的长字就一定是平水韵七阳平声，而年长、生长这种就是平水韵 二十二养上声，而身无长物，就是平水韵 二十三漾去声。这中检测也是需要大模型或者大量的词语训练检测，如果无法支持就保留一套API

### 推荐算法

可能涉及到大模型

1. 当检测出律情况：推荐如何补救，如通过修改平仄、替换合适的字保证押韵等实现基础格律诗词要求
2. 当检测不对仗的情况：推荐替换词语，给出合理的对仗
3. 根据题目、体裁、题材、押韵等，自动完成诗体的书写
4. 结合全诗，根据出句完成对句，根据对句完成出局
5. 结合全诗，自动推荐填字
6. 推荐字眼：五言诗第三字要响，七言诗第五字要响。对已有的诗局中重点斟酌字眼的下字

## AI

上面的高级检测和推荐算法中，一般都需要llvm大模型的支持。这里推荐使用目前最常用的大语言模型对话形式的方式设计，比如采用claude或者openai的baseurl接口规范，提供api_key、model_id、输入token、输入上下文、输入skill等数据，通过API获取到大模型的对话结果，就能很方便实现检测和推荐算法了

### SKILL

对于各种检测和推荐，最重要的是提供精确的、完整的、专业的skill，所以需要编写一份或者多份SKILL.md文件告知大模型如何去检测和输出符合规范的结果。

### 输出格式

建议规范化输出格式，或者用json格式返回出来，比如对于

* 检测类SKILL：按照SKILL中规范化的问题描述格式，直接输出检测的问题位置、问题原因
* 推荐类SKILL：直接输出推荐的诗词、字等文字即可（可能有多个推荐，则以列表形式），符加推荐的理由

## 设计要求

1. 模块化设计

每种检测可以使用职责链模式，每个检测算法设计成最小单元的独立化逻辑，比如检测平仄就只检测平仄、检测押韵就只检测押韵等。方便独立维护，甚至独立算法的升级

简单检测、高级检测和推荐模块也区分独立单元模块。

以上用到的AI模块也抽取成独立的业务无关的AI模块，提供最基础的API给上面的检测、推荐业务模块调用

2. SKILL设计

独立维护写成多份文档，用最清晰、最直白、最专业的文字描写清楚。一定要从网上或者论文中获取最贴近中国古典诗词的写作技巧，来指导AI进行思考和回答，必要时给出相关的连接和参考，让AI也去搜索了解。

3. 编码规范

 * 重点API和算法必须完善注释，但是不要将特例化代码注释上去，而是面向通用化注释编写。比如说明该API的作用，而不是说该API是具体给哪个模块用、那个算法调用
 * 尽可能使用最少代码完成最完整的功能
 * 尽可能将业务无关代码单独提取到工具、通用、基础这种概念的目录中去
 * 尽可能使用面向对象编码原则
 * 尽可能不要写死代码、魔法数字、常量等。而是提取到统一定义常量的文件/类中、统一管理宏/数字/字符串等文件/类中
 * 尽可能多依赖三方库来实现一些成熟的算法逻辑等，减少造轮子
 * 尽可能使用行业良好的API命名方法，要简单易懂易用，不要太长，不要不易理解。
 * 对外提供的API尽可能少而全，不要一股脑将API全部给出去，必要时可以使用桥接模式封装给出去

4. 文档规范

 * 文档统一管理，所有文档放到docs目录（除了CLAUDE.md、README.md等非技术、业务文档）命名规范：
   `v${version}-文档名称-${yyyymmdd}.md`，version表示当前版本，yyyymmdd表示年月日（如20261001），
   同类型的文档一般只有版本号、时间不一样，文档名称要保持一致
 * 对于算法、核心机制、业务逻辑、检测流程、推荐逻辑等可以分别写文档重点描述清楚
 * 每次修改了代码后，要更新文档，确保代码和文档保持最新同步

5. 目录设计（仅供参考）

```txt
cn-poetry-meter-check
└── docs 存放文档的目录，不需要分子目录
    src 源码目录
    ├── utils 一些通用的工具、变量、常量、配置等
    └── modules 各种大模块
        ├── base 基础检测模块
        │   └── ... 各种基础的检测算法文件类
        ├── advanced 高级检测模块
        ├── recommand 推荐算法
        └── ai 通用AI模块
    skills SKILL.md技能目录
        └── 技能目录名称
        │   └── SKILL.md
        └── ...
    models 离线模型目录，如果有才需要，否则不提供
    tests 测试目录
    example 示例网页
    ├── index.html
    ├── app.js
    └── app.css
```
